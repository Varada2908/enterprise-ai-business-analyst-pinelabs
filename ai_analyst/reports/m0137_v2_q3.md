# Our success rate in the last two weeks looks worse than the two weeks before. What changed?

## Answer
The success rate drop in the last two weeks is heavily concentrated in a single merchant and platform combination—merchant M0137 (Zestora Online Mart) on Android—which broke on October 12, 2026. This degradation was driven by a sharp surge in GATEWAY_ERROR and GATEWAY_TIMEOUT failures originating from that integration.

## Findings (shown by the data)
1. Merchant M0137 on Android experienced a sharp drop in success rate starting on 2026-10-12, falling from 88.69% to 62.05% and contributing -0.527 pp to the overall success rate drop.  
   _Evidence: Q1 · ✓ numbers verified against evidence_
2. Merchant M0137 Zestora Online Mart is the top negative driver overall, with its success rate dropping by 16.35 pp between the baseline and current periods.  
   _Evidence: Q2 · ✓ numbers verified against evidence_
3. The failure reason shift shows a massive increase in GATEWAY_ERROR (surging by 0.463 pp of total attempts, with M0137 / ANDROID contributing 142 failures) and the emergence of GATEWAY_TIMEOUT (33 failures, all in M0137 / ANDROID).  
   _Evidence: Q3 · ✓ numbers verified against evidence_

## Hypotheses (possible drivers, not proven)
1. **An app update or gateway integration change made by merchant M0137 on their Android application around October 12 introduced connection or payload errors.**  
   Why plausible: The failure is strictly isolated to merchant M0137 on Android and manifests as gateway errors and timeouts rather than bank or network issues.  
   Consistent with: Q1, Q2, Q3 · To verify: Check merchant M0137's release history or API integration logs around October 12, 2026.

## Caveats
- The analysis spans transactions up to October 25, 2026, covering a 2-week comparison window before and after October 12.
- Some failed rows lack a failure code, though the dominant spike in gateway errors is unmistakable.

## Suggested follow-ups
- Inspect the specific API error payloads returned to M0137 on Android.
- Contact merchant M0137 technical support to notify them of the gateway error surge.
- Examine request volume patterns for M0137 to see if retry storms contributed to timeouts.

```sql
    SELECT txn_date, sum(n) OVER (ORDER BY txn_date ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING) AS total_after
    FROM overall

cum AS (
    SELECT dimension, segment, txn_date AS change_date,
           sum(n) OVER wb AS n_before, sum(s) OVER wb AS s_before,
           sum(n) OVER wa AS n_after, sum(s) OVER wa AS s_after
    FROM daily
    WINDOW wb AS (PARTITION BY dimension, segment ORDER BY txn_date
                  RANGE BETWEEN INTERVAL 28 DAYS PRECEDING AND INTERVAL 1 DAYS PRECEDING),
           wa AS (PARTITION BY dimension, segment ORDER BY txn_date
                  RANGE BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING)
),
scored AS (
    SELECT c.dimension, c.segment, c.change_date, c.n_before,
           round(c.s_before::DOUBLE / c.n_before, 4) AS sr_before, c.n_after,
           round(c.s_after::DOUBLE / c.n_after, 4) AS sr_after,
           round(c.s_after::DOUBLE / c.n_after - c.s_before::DOUBLE / c.n_before, 4) AS sr_change,
           round(c.n_after::DOUBLE / oa.total_after
                 * (c.s_after::DOUBLE / c.n_after - c.s_before::DOUBLE / c.n_before) * 100, 3) AS impact_on_overall_sr_pp,
           -- two-proportion z-score: how clearly the rate broke (ranks sharp breaks above slow drift in big segments)
           round((c.s_after::DOUBLE / c.n_after - c.s_before::DOUBLE / c.n_before) / NULLIF(sqrt(
                 ((c.s_before + c.s_after)::DOUBLE / (c.n_before + c.n_after))
                 * (1 - (c.s_before + c.s_after)::DOUBLE / (c.n_before + c.n_after))
                 * (1.0 / c.n_before + 1.0 / c.n_after)), 0), 2) AS z_score,
           bounds.d1 AS data_end
    FROM cum c
    JOIN overall_after oa ON c.change_date = oa.txn_date
    CROSS JOIN bounds
    WHERE c.n_before >= 100 AND c.n_after >= 100
      AND c.change_date >= bounds.d0 + INTERVAL 14 DAYS
      AND c.change_date <= bounds.d1 - INTERVAL 6 DAYS
      AND c.s_after::DOUBLE / c.n_after < c.s_before::DOUBLE / c.n_before
),
best AS (
    SELECT * FROM scored
    QUALIFY row_number() OVER (PARTITION BY dimension, segment ORDER BY z_score ASC, change_date) = 1
)
SELECT * FROM best ORDER BY z_score ASC LIMIT 12
```

### Q3 · [driver scan] failure-reason shift (2026-09-28..2026-10-11 vs 2026-10-12..2026-10-25)
```sql
WITH valid_txn AS (
    SELECT * EXCLUDE (_rn)
    FROM (
        SELECT t.*, pm.method_code,
               CAST(t.created_at AS DATE) AS txn_date,
               row_number() OVER (PARTITION BY t.transaction_id ORDER BY t.updated_at DESC) AS _rn
        FROM transactions t
        JOIN payment_methods pm USING (payment_method_id)
    )
    WHERE _rn = 1
      AND status IN ('SUCCESS', 'FAILED', 'USER_CANCELLED', 'PENDING')
      AND amount > 0 AND amount <= 1000000
),
base AS (
    SELECT v.*, b.short_name AS bank, m.merchant_name, m.category AS merchant_category,
           CASE WHEN v.txn_date BETWEEN DATE '2026-10-12' AND DATE '2026-10-25' THEN 'cur'
                WHEN v.txn_date BETWEEN DATE '2026-09-28' AND DATE '2026-10-11' THEN 'base' END AS period
    FROM valid_txn v
    LEFT JOIN banks b ON v.bank_id = b.bank_id
    LEFT JOIN merchants m ON v.merchant_id = m.merchant_id
    WHERE v.status IN ('SUCCESS', 'FAILED', 'USER_CANCELLED') 
),
fc AS (
    SELECT coalesce(failure_code, '(missing)') AS failure_code,
           count_if(period = 'base' AND status = 'FAILED') AS failed_base,
           count_if(period = 'cur' AND status = 'FAILED') AS failed_cur
    FROM base WHERE period IS NOT NULL GROUP BY 1
),
tot AS (SELECT count_if(period = 'base') AS n_base, count_if(period = 'cur') AS n_cur FROM base),
seg_fail AS (
    SELECT coalesce(failure_code, '(missing)') AS failure_code,
           coalesce(merchant_id, '(none)') || ' / ' || device_platform AS segment, count(*) AS n
    FROM base WHERE period = 'cur' AND status = 'FAILED' GROUP BY 1, 2
),
top_seg AS (
    SELECT * FROM seg_fail
    QUALIFY row_number() OVER (PARTITION BY failure_code ORDER BY n DESC, segment) = 1
)
SELECT fc.failure_code, failed_base, round(failed_base::DOUBLE / n_base * 100, 3) AS pct_of_attempts_base,
       failed_cur, round(failed_cur::DOUBLE / n_cur * 100, 3) AS pct_of_attempts_cur,
       round((failed_cur::DOUBLE / n_cur - failed_base::DOUBLE / n_base) * 100, 3) AS change_pp,
       top_seg.segment AS top_merchant_platform_cur, top_seg.n AS top_segment_failed_cur
FROM fc CROSS JOIN tot LEFT JOIN top_seg ON fc.failure_code = top_seg.failure_code
ORDER BY change_pp DESC
```
